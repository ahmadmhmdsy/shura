### The bridge

Tailwind 4 only emits a colour utility from a `--color-*` theme entry, so the 177 bare `sura-*`
classes used across the app compiled to nothing. `@theme inline` in `src/styles/globals.css` now
declares eight aliases, each pointing at the token matching the role the class is actually used in:

| Utility | Resolves to |
|---|---|
| `bg-sura-bg` | `--sura-surface-primary` |
| `bg-sura-panel` | `--sura-surface-elevated` |
| `border-sura-border` | `--sura-border-primary` |
| `text-sura-foreground` | `--sura-text-primary` |
| `text-sura-muted` | `--sura-text-secondary` |
| `text-` / `bg-` / `border-sura-accent` | `--sura-accent-primary` |
| `text-` / `border-sura-warn` | `--sura-warning` |
| `text-` / `bg-` / `border-sura-danger` | `--sura-error-text` |

No call site was renamed, so the two specs that assert `text-sura-accent` / `text-sura-danger`
(`features/settings/ProviderKeyCard.spec.tsx`) still pass unchanged.

### Contrast

Every foreground/background pair the components actually render was measured in both themes
(OKLCH -> OKLab -> linear sRGB -> WCAG relative luminance, 10% tints composited in linear light).
The axe `color-contrast` violation in `e2e/app.spec.ts` was one of them: the dark-mode accent
fill `#00bb87` with a near-white label is 2.34:1. Each token's lightness was then solved for the
worst surface it is painted on:

- light: `accent-primary` 0.55 -> 0.46, `accent-secondary` 0.65 -> 0.49, `accent-tertiary` 0.75 ->
  0.52, `success` 0.60 -> 0.48, `warning` 0.70 -> 0.52, `error` 0.55 -> 0.53, `info` 0.60 ->
  0.48, `text-tertiary` 0.55 -> 0.50, `border-accent` 0.70 -> 0.62
- dark: `accent-foreground` 0.98 -> 0.16 (the fill stays bright, so its label has to go dark)
- new tokens: `--sura-error-text` (0.52 light / 0.84 dark) for danger **text**, and
  `--sura-error-foreground` (0.98 / 0.16) for the label on a solid danger fill
- `--sura-chat-user-bg` / `--sura-chat-user-text` and `--sura-input-border-focus` are now
  `var(--sura-accent-*)` aliases, so the bubble pair and the focus ring cannot drift from the accent

All 25 text pairs, the 2 non-text pairs and the 4 tint composites now clear 4.5:1 / 3:1 in both
themes. The axe `color-contrast` violation is gone; `nested-interactive` is a markup defect
outside token scope, so the e2e axe test stays red until that is fixed separately.

### Deviations from plan section 4.4

- **`--sura-warning-text` and `--sura-accent-text` are not needed.** The plan asked for three dark
  semantic text tokens; measurement shows the base `--sura-warning` and `--sura-accent-primary`
  already pass as text once their lightness is solved, so extra aliases would be a second owner for
  the same value. Only `--sura-error-text` was added.
- **Aspect ratios are not tokenised.** Nothing in the app sets an `aspect-*` utility, so there is
  no value to own. `shapes.css` documents the omission instead of inventing a scale.
- **Breakpoints are not tokenised.** Only `sm:` and `md:` are used, and Tailwind's own scale is
  already the single owner of those numbers.
- **Component migration is not part of this phase.** `dimensions.css` and `shapes.css` define the
  scale; components still use the equivalent Tailwind literals (`size-4`, `h-9`, `max-w-md`).
  The mapping is recorded in each file's header. Migrating them is the next block of work.

### Font

`@fontsource/ibm-plex-sans-arabic` 5.3.0 is now a dependency and `src/main.tsx` imports the four
weights the components use (400/500/600/700). Bundled rather than linked, so the desktop build
never fetches a font at runtime. `--sura-font-sans` now resolves to a face that is actually
loaded instead of falling back to Segoe UI / Tahoma.

### Lint rule

`eslint.config.js` gained a `no-restricted-syntax` block over `src/**/*.{ts,tsx}` that rejects raw
hex literals, raw colour functions, and the `*-white` / `*-black` utilities (the design system has
no white or black token, so those would break dark mode). The codebase has zero violations today, so
it is a regression guard; it was verified to fire on all three violation types and to stay silent
on `var(--sura-text-primary)`.

## Follow-up - composer send behaviour  [DONE]

Requested after the i18n work: the chat input should clear when the request is sent and keep the
keyboard focus, so a follow-up can be typed without reaching for the mouse.

- Clearing lives in `doSend()` in `src/features/chat/ChatScreen.tsx` - the single funnel used by both
  the Send button and the Ctrl+Enter shortcut - so the two paths cannot drift apart.
- It runs **before** `await persistTurn(turn)` for immediate feedback. That is safe because
  `persistTurn` is handed the local `turn` object built two lines earlier, not the store value, so
  emptying the store cannot lose the prompt.
- Focus is plumbed through React 19's ref-as-prop: `ComposerProps` gained
  `ref?: Ref<HTMLTextAreaElement>` and the shared-prompt `Textarea` receives it; `doSend` calls
  `composerInputRef.current?.focus()` beside the clear.
- Only `sharedPrompt` is cleared. The per-target advanced prompts (`customs`) are deliberately left
  intact so one send cannot silently wipe a multi-target setup. **This is a product choice, not a
  constraint** - it flips trivially if the other behaviour is wanted.

Verified in a real browser against the production build (`browser` project + mock provider, three
scenarios): the Send button clears and refocuses, Ctrl+Enter clears and refocuses, and a second send
after the first still works. All three PASS.

## Follow-up - six composer UX suggestions  [DONE]

Approved by the user and implemented. All six are composer/chat-surface changes; none of them
touches the localization or token layers, but every new string went through en.ts + ar.ts and
every new style value through the existing tokens.

| # | Suggestion | Where |
|---|---|---|
| 1 | Focus the composer when the active session changes | ChatScreen.tsx focus effect + autoFocusComposer prop from App.tsx |
| 2 | Escape clears the draft, with an undo | Composer.tsx handleSharedKeyDown |
| 3 | Cap the textarea's auto-growth | Composer.tsx shared Textarea |
| 4 | Show a visible send / newline hint | Composer.tsx action row |
| 5 | Show a prompt length counter | Composer.tsx action row |
| 6 | Setting: also clear the per-target prompts on send | composerStore, settingsStore, ClearCustomsToggle, ChatScreen.doSend |

- **#1 needed a different shape than planned.** App.tsx renders <ChatScreen key={currentSession.id} ...>,
  so the component *remounts* on every session switch and a useRef guard would never fire. The
  existing 'focus <main> on session switch' effect already skipped when focus was inside
  [data-composer], so it was extended to focus the composer first and keep <main> as the
  fallback. App passes autoFocusComposer={!showOnboarding} so the modal first-run wizard keeps
  focus; when it closes, the effect re-runs and the caret lands in the field.
- **#2 is inert while a send is streaming.** Escape is already the stop shortcut there
  (useChatShortcuts), and wiping the draft at the same moment would be a surprise. The undo is a
  sonner toast action, so the text is recoverable rather than merely acknowledged.
- **#3 reuses tokens that already existed.** --sura-composer-min-height (5rem) and
  --sura-composer-max-height (12rem) were declared in dimensions.css but unused; the base
  Textarea already sets field-sizing-content, so only the cap was missing.
- **#4 states the real binding.** The hint reads 'Ctrl+Enter to send / Shift+Enter for a new line'
  because Ctrl+Enter is what useChatShortcuts binds; a bare 'Enter to send' would be wrong.
- **#5 is hidden while the field is empty** and reads through formatNumber, so it stays Latin-digit
  under Arabic per D1. aria-label carries the full 'N of M characters' sentence.
- **#6 defaults to off.** The per-target prompts are a deliberate multi-target setup, so the
  previous behaviour (keep them) is the default and the setting opts into wiping them. It is wired
  through the existing applyChange rollback and the persist() snapshot, so a failed write rolls
  it back like every other setting.

New resources, in both catalogs: common.undo, chat.draftCleared, chat.sendHint,
chat.promptLength, chat.promptLengthOf, settings.clearCustomsOnSend,
settings.clearCustomsOnSendDesc.

Tests: 5 new cases in Composer.spec.tsx (hint + counter, Escape clears, Escape inert while
sending, Escape inert when empty, max-height class) and 2 in ChatScreen.spec.tsx (the setting
wipes customs; without it they survive). sonner is mocked in Composer.spec.tsx because
jsdom renders no <Toaster />.

## Notes / findings

- **Deliberate deviation from "remove all 12 hardcoded `dir` attributes"**: every `dir="rtl"`
  is gone (it fought the locale), but `dir="ltr"` is intentionally kept on inherently-LTR
  technical content - the `<pre>` stack trace in `ErrorBoundary.tsx` and the percentage spans in
  `RagStatusChip.tsx`. Direction is otherwise set once on `document.documentElement`.
- `src/i18n/UiText.spec.ts` wraps the shared-instance reset in `act(...)`, because the singleton is
  module state and a mounted `useUiText` consumer would otherwise warn about an update outside `act`.
- `language` is persisted in the existing `settings.main` Dexie record, so a pre-existing record
  without the field falls back to `DEFAULT_LOCALE` through the store defaults.
- `LanguageSwitcher` applies the locale to `UiText` first and persists second; a failed write rolls
  the visible locale back to the stored one.
- `ChatScreen` internal `throw new Error(...)` messages now come from `chat.internal.*`. The Arabic
  values are byte-identical to the previous literals, so existing assertions still pass.
- The document title is localized too: `UiText.applyDocumentLocale()` sets `dir`, `lang`, and
  `document.title` from `app.name`; `index.html` keeps `dir="rtl" lang="ar"` and `<title>شورى</title>`
  purely as the pre-boot default, matching `DEFAULT_LOCALE`.
- Six existing specs asserted the **old, grammatically wrong** Arabic count wording ("3 قطعة",
  "2 ملف", "1 ملف"). They were updated to the CLDR-correct forms the plural resources now produce
  ("3 قطع", "قطعة واحدة", "ملف واحد", "قطعتان", "ملفان مفهران", "3 نتائج بحث"). No product behavior
  changed apart from the wording itself.
- `SettingsScreen.spec.tsx` used positional `getAllByRole("combobox")[0|1]`; the language picker is
  also a combobox, so those queries were changed to look the selects up by accessible name.
- Arabic-first plural rendering slightly changes single-count wording (for example "أخطاء: نتيجة واحدة"
  instead of "أخطاء: 1 نتيجة"); `sessions.count` renders "3 جلسات" (few) rather than "3 جلسة".
- **`SettingsScreen` anchor ids - FIXED.** The section ids were derived from the localized title with
  `title.replace(/s+/g, "-")`, a pre-existing regex bug (the class should be `\s+`). Two defects fell
  out of it: the ids were the Arabic titles verbatim (`section-اللغة`), so every anchor changed with
  the language and a deep link broke on a locale switch. `CollapsibleSection` now takes a stable
  `id` prop and emits `id={"section-" + id}`; all nine call sites pass a slug
  (`language`, `providers`, `primary-model`, `session-dir`, `rag-settings`, `rag-files`,
  `rag-external`, `timeout`, `dev-log`), and both the TOC `href` and the scroll lookup use the same
  helper. Verified in the browser: `ar` and `en` both yield the identical nine ids, all matching
  `/^[a-z0-9-]+$/`.
- Coverage baseline before this work: 94 test files / 957 tests, ~86% functions (threshold 80).
- **Bundle impact:** the base chunk grew from 1,071.15 kB to **1,095.92 kB** (+24.77 kB) because both
  locale catalogs are statically imported. The 1,200 kB budget still has 104.08 kB of room, but a third
  language would cost roughly the same again unless the catalogs become lazily loaded. Recorded in
  `docs/environment.md` section 9, not fixed.
- **The browser e2e gate is red at `HEAD` and the remaining failures are not regressions.** Two
  infrastructure defects were repaired here; the rest are pre-existing and documented in
  `docs/environment.md` section 12.
- **`boot()` - FIXED.** `e2e/app.spec.ts` navigated and immediately asserted the `شورى` heading, but on
  a fresh profile the first-run wizard is modal and `aria-hidden`s the app behind it, so
  `getByRole("heading", { name: "شورى" })` resolved to the two headings *inside* the dialog and every
  one of the 12 scenarios died in `beforeEach`. The fix sets `shura-onboarding-seen` in
  `page.addInitScript` before any app code runs - the same approach `tauri-app.spec.ts` already used.
  This is deterministic rather than a timing fix, so it also removes the flaky 390px scenario.
- **`browser` project `testIgnore` - FIXED.** `e2e/tauri-app.spec.ts` ran inside the `browser` project
  although it drives the tauri-playwright fixture and waits for `window.__PW_ACTIVE__`, which a plain
  browser never defines. The `tauri` project already excluded `app.spec.ts`; the mirror line was
  missing. Four spurious failures removed.
- **Still failing, deliberately untouched (4 + 1 + 1 scenarios):** `resultCards()` in `e2e/app.spec.ts`
  is `[role="status"]:not(.sr-only)`, and `RagStatusChip` carries `role="status"` ahead of the card in
  DOM order, so `.first()` lands on "لا توجد ملفات مفهرسة بعد" (4 scenarios); the retry scenario waits
  for a switch that only renders with two or more targets while it adds one; and axe still reports
  `nested-interactive` plus the `landmark-*` / `region` violations, which are real HTML-structure
  defects in the app rather than token or localization issues. `color-contrast` was fixed in Phase 1.
  Fixing these means changing test selectors and product markup, so they need an explicit decision.
